## What was verified, and how

1. **stdout discipline** — `grep -rnE 'os\.Stdout|fmt\.Print|log\.New\(os\.Stdout|println\(|print\('` over every `.go` file returns nothing. All logging goes through `internal/logger.New` (`internal/logger/logger.go:14`, `log.New(os.Stderr, …)`) and mautrix's `zerolog.New(os.Stderr)` (`internal/matrix/client.go:132`). The only stdout writer is the SDK's `StdioTransport`, which wraps `os.Stdout` in a `nopCloserWriter` (`go-sdk/mcp/transport.go:137`); the SDK's own logger is `slog.DiscardHandler` when unconfigured (`go-sdk/mcp/logging.go:112`), so it writes nothing.
2. **goroutine lifetime / races** — traced main (`cmd/server/main.go:48-126`): signal watcher, sync loop, dispatcher workers, and HTTP server all share the run context; SIGINT/SIGTERM cancels it, `dispatcher.Close()` and `matrixClient.Close()` join their WaitGroups, and `wg.Wait()` joins the rest. The sync loop returns nil on `ctx.Done()`/`isClosed` (`internal/matrix/client.go:449`), the dispatcher queue send is non-blocking (`internal/trigger/dispatcher.go:147-151`) and the queue is never closed, so no send-on-closed-channel or blocked-send path exists. The `bgWG.Add(1)` in `init` is serialized against `Close` via `closeMu` (`internal/matrix/client.go:524-531` vs `559-573`), so `Add` happens-before `Wait`. `go test -race ./...` passes, but with `[no test files]` in all six packages, so it exercised no concurrent paths — static reasoning above, plus the race detector, is the evidence.
3. **backfill / self-message filtering** — `DontProcessOldEvents` is registered on the syncer before the first sync (`internal/matrix/client.go:519-522`, inside `init`, called from `syncOnce` before `SyncWithContext`). In mautrix v0.33 it returns `false` on the initial sync (`since == ""`), which makes `DefaultSyncer.ProcessResponse` return before dispatching any events (`mautrix/sync.go:96-100, 225-233`); on later syncs it strips rooms the bot just joined. Self-sent events are dropped in the `Client.OnEventType` wrapper before the handler runs (`internal/matrix/client.go:163-170`), which is the only path into `Dispatcher.Handle` (`cmd/server/main.go:56`), so the filter precedes both the ring buffer and webhook enqueue.
4. **ring buffer** — `[BufferSize]Trigger` with `BufferSize = 100` (`internal/trigger/dispatcher.go:24-32, 62`), `sync.RWMutex`-protected. `Recent` walks `next-1` backward (newest first) and returns `Timestamp > since` (strictly newer, matching the "newer than" contract, no off-by-one), stable-sorts by timestamp descending, and clamps limit to 100 (`dispatcher.go:157-175`). Traced pre-wrap (count<100, entries at ring[0..count-1]) and post-wrap (count=100, next wraps and overwrites oldest) — ordering and eviction are correct.
5. **webhook dispatch** — async via 4 workers and a 256-buffer queue; enqueue is `select … default` so it never blocks the sync loop (`dispatcher.go:138-152, 189-219`). 5s timeout is enforced twice (`http.Client{Timeout: webhookTimeout}` and `context.WithTimeout` in `post`), exactly one retry after 500ms (`deliver`), and failures are logged and dropped; the response body is drained and closed (`dispatcher.go:221-261`). Bursts are bounded by the queue cap plus worker count. Body is the marshalled `Trigger` over POST.
6. **send_message** — empty allow-list rejects everything (`sendGate.check`, `internal/mcpserver/server.go:276-296`), a non-listed room is rejected before the token is touched, empty/whitespace text is rejected before the gate (`server.go:212-224`), and a single mutex-guarded `next` timestamp enforces one accepted send per 3s across all rooms; two concurrent sends cannot both pass because `next` is set under the same lock. Errors are actionable (`rate limited, retry in Ns`, room name in the not-allowed error).
7. **secrets** — `grep -rniE 'syt_|access.?token|…|bearer '` over the tree and `git log -p --all` show only variable names, redaction code, and docs; no tokens, passwords, pickle keys, or `.env` contents are committed. `.env` is ignored. Config error messages name variables only (`config: MATRIX_HOMESERVER: required but not set` observed at runtime) and `Config.String`/`GoString` redact `AccessToken`, `PickleKey`, and the webhook URL (`internal/config/config.go:80-102`).
8. **MCP surface** — exactly four tools (`internal/mcpserver/server.go:74-100`). Dumped the live schemas via an in-memory client/server connect: the three read tools carry `readOnlyHint: true`; `send_message` carries `destructiveHint: true`, `idempotentHint: false`, `readOnlyHint: false`. Schemas mark `room_id`/`text` required on their tools, `limit`/`since_timestamp` optional with documented defaults, and `list_rooms` has an empty object schema. `clampLimit` (default 20, max 100) is applied in both read tools (`server.go:175, 197, 226-235`) and re-clamped in `matrix.Messages`.
9. **config** — every documented variable is read exactly once in `LoadFrom` (`internal/config/config.go:125-187`); required vars fail with a joined `*config.VarError` (`errors.Join`), and defaults are sane (`:8080`, `matrix-crypto.db` when E2EE is on). `Config.String()`/`GoString` redact secrets, and no error path echoes a value.
10. **build hygiene** — `go mod tidy -diff` clean; `gofmt -l .` clean; `go build ./...` and `go vet ./...` pass; `go test -race ./...` passes with `[no test files]` everywhere (tests are a Phase D item, not a blocker). The built binary run with `env -i` exits 1 with `config: MATRIX_HOMESERVER/MATRIX_USER_ID/MATRIX_ACCESS_TOKEN: required but not set` and no values. The one gap is F1: the `-tags goolm` build requirement is not documented.

## Could not verify

- **Live Matrix behaviour** — no homeserver or credentials exist here, so the sync loop, E2EE decryption, `list_rooms` probes, and the actual `send_message` path were not exercised end-to-end. Backfill/self-filter conclusions come from reading mautrix v0.33 source plus code inspection, not a live sync.
- **Webhook in flight** — no live webhook endpoint to observe the 5s timeout and single retry; behaviour is verified by inspection of `deliver`/`post`.
- **SSE stream lifetime** — F3 is established from the SDK (`http.NewResponseController` flush, no hijack) and net/http deadline semantics, not reproduced against a live Streamable HTTP client.
- **Race detector coverage** — `-race` had no concurrent test surface (no tests), so its pass only confirms clean compilation under the race detector, not race-freedom.
